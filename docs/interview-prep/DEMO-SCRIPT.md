Credentials are identical in the app and portal. **Two devices:** laptop (admin portal) + phone (Flutter app). If no phone, run the app as the web build on the laptop.

## Sequence

### 1. Customer creates a request (mobile, ~2 min)
1. Open the app → login with `customer@quickserve.demo`.
2. Home → shows **My Requests** count + recent list (REQ-2026-000001/000002 completed, 000003/000004 active).
3. Tap **Create Service Request** → pick a service (e.g. **AC Service**), description, preferred date/time, address, priority **High** → Create.
4. App returns the new ticket: **REQ-2026-00000X · CREATED · HIGH** and adds it to history.

> Say: "The code was generated by a DB trigger, the audit event `REQUEST_CREATED` was written server-side, and I can't fake a different customer's request — RLS."

### 2. Agent picks it up (mobile, ~1.5 min)
1. Log out → login as `agent@quickserve.demo`.
2. **Assigned Requests** shows the ticket.
3. Update status: `assigned → accepted → in_progress → completed` (open the ticket, tap through).
4. Switch back to the customer account → reopen the ticket → **history** shows each transition + who changed it.

> Say: "Each transition was validated by the trigger — no skips, no jumps from a closed ticket."

### 3. Admin portal (laptop, ~2 min)
1. Open `http://localhost:5173` → login `admin@quickserve.demo`.
2. **Dashboard** → stat cards (total/new/completed).
3. **Requests** → search filter (e.g. type "REQ-2026-000003", or filter by status) → open details modal → note the audit + history.
4. **Audit log** → show `REQUEST_CREATED`, `REQUEST_ASSIGNED`, `REQUEST_UPDATED`, `LOGIN_SUCCESS`, `AUTHORIZATION_FAILED` rows with actor + timestamp.
5. Show **People** (customers/agents).

> Say: "Only an admin sees this panel — a customer or agent trying to sign in here writes `AUTHORIZATION_FAILED` to the audit trail instead."

### 4. Prove security quickly (30 s, if they ask)
- In the admin portal, show that you CAN'T delete/edit a customer's raw request without going through rules (or verbally: "try changing the request UUID in the client — you get zero rows").

## Demo "don'ts"

- Don't demo **signup** live (email-confirm may block). Prefer instant login; mention signup exists and the app now handles the confirm flow gracefully.
- Don't demo status **skips** or invalid transitions as a feature — frame them as *blocked by the DB* if asked.
- Don't log out of the admin portal at the end in a way that leaves a blank screen — leave it on the audit log tab.
