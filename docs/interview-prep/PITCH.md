## 30-second pitch

> "QuickServe is an on-demand home-services platform I built end to end — a Flutter
> mobile app for customers and agents, a React admin portal, and a PostgreSQL +
> Supabase back end. The key decision I made was to enforce **all security and
> business rules in the database itself**, using Row Level Security and SECURITY
> DEFINER RPCs, rather than trusting the client app. I proved it with a 16-case
> automated authorization test that shows, for example, one customer can never read
> another customer's request, even if they tamper with the request — and a full
> audit trail records every action."

## One-liners

- **Product:** customers request home services; agents get assigned and update work; admins operate a dashboard with search, people and a full audit trail.
- **Stack:** Flutter (mobile) · React + Vite (admin web) · Supabase = PostgreSQL + Auth + RLS (backend).
- **Security:** authorization lives in the database, not in the UI — RLS on all 5 tables + validated RPCs + trigger-enforced state machine.
- **Proof:** `tests/rls-authz.mjs` — 16 live assertions against a real Supabase project.

## The 5 things I want the panel to remember

### 1. Authorization decided by the database, not the app
- RLS enabled on all application tables (`001_schema.sql:463+`), `authenticated` only.
- Role is read server-side via `current_user_role()` (SECURITY DEFINER, `001_schema.sql:182`) — a tampered client can't claim a role.
- Even a modified request UUID returns **zero rows** for an unauthorized customer (policy `requests_select`).

### 2. All writes go through validated RPCs
- `create_request` (`:334`) and `update_request_status` (`:391`) are SECURITY DEFINER with **locked `search_path`** and parameterized inputs (no SQL injection surface).
- Raw `UPDATE` on `service_requests` is **admin-only** by policy; agents/customers must use the RPC, which re-checks ownership, role, and legal transition.

### 3. Lifecycle is enforced server-side
- `validate_status_transition()` trigger (`:235`) blocks illegal status jumps for *all* writers: `created→assigned|cancelled`, `assigned→accepted|cancelled`, `accepted→in_progress`, `in_progress→completed`; terminal states are dead ends.
- Request codes `REQ-2026-000NNN` generated by trigger (`:109`), unique.

### 4. Complete, tamper-resistant audit trail
- `audit_logs` has **no insert/update/delete policies** — only admin can read; writes happen server-side.
- `write_audit` (`:196`) allow-lists events (`LOGIN_SUCCESS`, `REQUEST_CREATED`, `AUTHORIZATION_FAILED`, …) and **never logs secrets** (no tokens/passwords/keys).
- Customer self-cancel and admin raw-write changes also flow through `record_request_history` (`:291`).

### 5. It's a tested, documented, live product
- 16/16 authorization tests (`tests/rls-authz.mjs`) incl. cross-customer read denial, role self-escalation denial, illegal-transition denial, audit isolation.
- Docs: `docs/ARCHITECTURE.md`, `docs/SECURITY.md`, `docs/DATABASE.md`, `docs/DEMO.md` + 12 live screenshots.
- Running live on Supabase; GitHub public (`Rutuja-kale06/quickserve`).
